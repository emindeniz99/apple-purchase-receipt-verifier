# Wasm ABI v1: one versioned call over four policy-free operations

Date: 2026-09-26. Code, scripts and raw results are in
`2026-09-26-wasm-abi-v1/`. Its `README.md` has the file table and the
commands to reproduce.

**Question.** Can round 4's template-build `aprv.wasm` expose one small,
versioned ABI with four operations that apply no policy? That ABI must:

- keep every cryptographic verdict and every endpoint answer;
- keep exactly its two imports;
- turn caller misuse into hard failures;
- cost nothing measurable against round 6?

This is a spike, not the production module. A second agent builds
`aprv-server` on this module next.

Labels: TESTED (ran here), EXPECTED (inferred, not run). Nothing under
`rust/`, `docs/rust-core` or any other production path changed, and
`DECISIONS.md` is untouched.

## Result

- **The ABI works as specified on Node and on Endive (TESTED).**
  - 33 of 33 mandatory tests pass on each host.
  - A wrong `abi_version` traps before any other argument is read and
    before any host import runs.
  - An unknown operation traps.
  - Invalid pointers, lengths and handles trap, and so do a double free
    and use-after-free.
  - Every verification failure is a value.
- **Cryptography is unchanged (TESTED).** On all 6,179 rows (the 1,179
  corpus rows plus 5,000 mutants):
  - 0 answers differ from round 4's native C ABI rows of the same source;
  - 0 traps;
  - every row that still has a cryptographic verdict gets the same verdict,
    reason and message;
  - every endpoint answer is byte-identical.

  Answers that changed by design are counted in their own categories
  (next section).
- **Endive is byte-identical to Node on all 6,179 rows (TESTED).** The one
  exception is `request_date*`, which comes from the wall clock on endpoint
  rows with no pinned clock.
- **No speed regression (TESTED).** Node and Endive are both within round
  6's noise band; the table is further down.
- **Imports are exactly `aprv.clock_now_ms` and `aprv.random_get` (TESTED).**
  The module is 2,952,613 bytes, sha256
  `b14e14b2c3b8a38953c6ac03d941e42647321fdb86cfb0e3629c006687b636b3`.

## The ABI

```text
aprv_abi_version() -> i32                         == 1
aprv_alloc(len) -> ptr        (0 when impossible)  aprv_dealloc(ptr, len)
aprv_call(abi_version, operation, ptr, len) -> handle
aprv_result_ptr(h) -> ptr   aprv_result_len(h) -> len   aprv_result_free(h)
```

| Op | Name | Natural input | Output (UTF-8 JSON) |
|---|---|---|---|
| 1 | VERIFY_RECEIPT | the `receipt-data` string (standard base64, UTF-8), decoded in the module by the Apple-measured strict rule | `{"verified":true,"payload":<receipt view>}` or `{"message","reason","verified":false}` |
| 2 | VERIFY_SIGNED_DATA | the compact JWS (UTF-8) | `{"verified":true,"payload":<claims>,"payloadJson":"<the signed payload JSON, exactly>"}` or the failure object |
| 3 / 4 | ENDPOINT_PRODUCTION / ENDPOINT_SANDBOX | the verifyReceipt request body | today's endpoint answer, byte for byte |

- **Order of checks in `aprv_call`.** It tests the version first, then the
  operation, then the input range. Only then does it run the operation.
  `results/aprv-call-head.txt` shows the built code: after the shadow-stack
  prologue, parameter 0 is the first thing read, and a mismatch branches
  straight to `unreachable`.
- **Traps.** A trap is `core::arch::wasm32::unreachable()`. There is no
  panic path and no message formatting.
- **Handles.** Result handles are 1-based slots, and freed slots are reused.
- **Mismatch messages.** The bridge turns a mismatch trap into "APRV Wasm
  ABI mismatch: module=1, caller=N" by asking `aprv_abi_version()`. It
  never reports a mismatch as `verified=false`.
- **No policy anywhere.** There is no bundle ID, environment or appAppleId,
  as the owner confirmed. The JWS path uses the core's `verify_raw`, which
  enforces no claim. The builder's mandatory `bundle_id`/environments are
  placeholders that are never compared.
- **Receipts are base64 only**, per the owner's answer. The module restates
  the core's crate-private `decode_receipt_string`: the same 3,145,728-byte
  cap, then `base64::decode_receipt_base64`, with the same messages.
  - `js/base64-rule.mjs` runs all 167 texts of the 33 `base64` cases in
    `fixtures/cases.json` through op 1. Every text lands on the expected
    side of the rule: 167/167.
  - The 19 `receipt-base64` rows run with full verdicts in the corpus.
- **Bridge lifecycle, the same in `js/abi.mjs` and `AprvAbi.java`:**
  1. alloc
  2. copy the input in
  3. `aprv_call`
  4. bounds-check ptr/len
  5. copy the result out
  6. `aprv_result_free`
  7. dealloc
  8. decode

  No guest pointer leaves a public call. After a trap the bridge runs
  nothing more in that instance and the caller discards it.

## Corpus parity (`results/node.txt`, `results/endive-calls.txt`)

`py/abi_calls.py` maps each row onto a call:

- **der-encoded** (3,822 rows, plus 12 that are also guid-dropped): DER
  receipt rows go in as canonical base64.
- **direct** (2,344): base64 receipt rows go in untouched.
- **guid-dropped**: device-hash rows lose the GUID. ABI v1 takes no GUID.
- **no call** (1 row): the Xcode endpoint environment. The endpoint ops
  are per environment.
- **Anchors or a pinned clock**: rows with either go through the test
  variants (op + 256).

`py/abi_compare.py` puts each answer into a category against the C ABI's
answer:

| Category | Rows | Meaning |
|---|---:|---|
| same-verified | 188 | both verified; payload objects equal |
| same-failure | 5,506 | same reason and same message |
| endpoint-same | 128 | endpoint answer byte-identical (`request_date*` masked when unpinned) |
| old policy verdict | 6 | the C ABI refused WRONG_BUNDLE_ID / WRONG_ENVIRONMENT / WRONG_APP_APPLE_ID; ABI v1 verifies and returns the claim for the caller |
| old device binding | 6 | the C ABI refused DEVICE_HASH_MISMATCH; ABI v1 takes no GUID |
| old typed model | 6 | the C ABI's typed transaction model refused a claim's JSON type; ABI v1 returns the claims untyped |
| old config refusal | 5 | the C ABI refused to build a verifier (empty roots, null bundle ID, Xcode endpoint) |
| old ABI inexpressible | 306 | a NUL inside a C string, or non-UTF-8 (C ABI status 101) |
| old DER only | 28 | DER with no acceptable base64 form: empty, or larger than the base64 cap allows. ABI v1 refuses the string exactly as the C ABI's own base64 entry does |
| **DIFFERENT** | **0** | |

"Old DER only" covers three kinds of row:

- the empty-DER rows;
- the `reject-der-one-byte-over-the-size-cap` rows (the same reason; the
  message now names base64);
- `receipt/accept-der-at-the-size-cap`. That DER is 3,145,728 bytes, its
  base64 is 4,194,304 characters, and it is refused. This is the one
  verdict that flips.

The flip follows from base64-only input: the largest receipt ABI v1 can
take is 2,359,296 bytes of DER.

## ABI tests (`js/abi-tests.mjs`, `endive/.../AbiTests.java`)

33/33 pass on Node 22.22.2 and on Endive 1.1.0 (JDK 21, ByteArrayMemory).

**Hard failures.** Each case below traps, and a fresh instance then
verifies g5:

- `aprv_call(0, 0x7fffffff, 0xfffffff0, 0x7fffffff)` and the same call
  with version 2;
- unknown operations 0, 5, 99, 255, 256, 261 and -1;
- a null input pointer with a length;
- input past the end of memory;
- an input range that overflows u32;
- `aprv_result_ptr/len/free` on handles that were never issued;
- a double free;
- use-after-free through `result_ptr` and through `result_len`.

**Values, not traps:**

- empty input;
- a garbage receipt;
- a non-UTF-8 JWS (`INVALID_JWS_FORMAT`);
- a malformed endpoint request, which answers `{"status":21002}`.

**Bridge behaviour:**

- A version mismatch through the bridge is an ABI error with the required
  text, and no host import runs during it.
- Absurd `aprv_alloc` lengths return 0 and the instance keeps working.
- Freed handles are reused.
- A result is a host-owned copy.
- Linear memory stays at 2,097,152 bytes over 2,000 further calls.
- Malformed result JSON is a host decode error, not a verdict.

## Speed (`results/bench.txt`)

The machine is a 4-core x86_64 VM with nothing else busy. The round-6
figures are round 4's module through round 5/6's C-ABI-shaped bridge.

| | ABI v1 | Round 6 |
|---|---:|---:|
| Node g5 receipt, mean µs (median of 3 × 1,000) | 1,343 | 1,434 |
| Node JWS, mean µs | 4,819 | 4,535 |
| Endive JDK 21 g5, calls/s at 1 / 2 / 4 threads | 154.7 / 323.0 / 482.2 | 153.1 / 327.0 / 463.7 |
| Endive JDK 21 JWS, calls/s at 1 / 2 / 4 threads | 52.6 / 101.9 / 166.8 | 48.8 / 97.0 / 152.3 |

- Every difference is inside round 6's ±10% run-to-run band.
- The ABI v1 figures include the base64 decode, both copies and the JSON
  decode.
- The 10/s/core floor holds with a wide margin on both hosts.

## Open questions for the design

- **The test variants (257 to 260).** They carry anchors and a pinned clock
  so the repository corpus can run through the ABI. Should they ship, or
  be built only into a conformance module? They cannot weaken trust by
  accident only if the host never exposes them.
- **Device binding (the GUID).** It is not in ABI v1. It would have to be a
  new operation.
- **The size flip.** Base64-only input lowers the largest acceptable
  receipt from 3 MiB of DER to 2.25 MiB of DER, because the 3 MiB cap
  applies to the base64 text. Apple's own endpoint takes base64, so this
  matches Apple.
- **Moving the decode into the core.** `decode_receipt_string` is
  crate-private, so the shim restates it. A production module would call
  one public core function instead.
- **Reporting a mismatch.** A version mismatch is a bare trap, and each
  bridge produces the message. A guest message would need a result or a
  side channel that the check-first rule forbids.

## Limits

- This covers wasm32-wasip1 only, on Node 22 and Endive 1.1.0 (JDK 21).
- Only the categories above are covered.
- The corpus's generated chains are exercised through the test envelope,
  not through the production operations. Only Apple-rooted rows (g5, the
  endpoint rows) exercise ops 1 to 4 themselves.
