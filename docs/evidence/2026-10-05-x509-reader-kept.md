# The core's X.509 reader, examined and kept

**Question.** `Certificate::is_readable` reads every certificate before
OpenSSL judges it: a version from 1 to 3, a signature `BIT STRING` of whole
octets, no extension OID carried twice, and a basicConstraints and a
keyUsage that decode. Does OpenSSL 4 already give each of those answers, so
that the reader can go (owner, Q57, 2026-10-05)? The answer decides whether
the core keeps the reader.

**Versions.** OpenSSL 4.0.2, built from source by `openssl-src`
400.0.1+4.0.2; source locations below are paths in that tarball. Rust
1.98.1, the test profile, on one Linux x86-64 container. The experiment ran
on 2026-10-05 on the branch `refactor/core-drop-x509-reader` (origin,
768e8f5 through bd1120c, not merged); the probes in
[`2026-10-05-x509-reader-kept/`](2026-10-05-x509-reader-kept/) were rerun
on 2026-10-06 over the commit that adds this note.

**Method.** Each rule was read against the OpenSSL source the core calls,
then removed, and the shared cases run (`cargo test --test conformance` in
`rust/`, 390 tests), with a probe that mints JWS chains under the test PKI,
each certificate signed as it stands, so only the reader stands between
them and `ok`. Two variants: the whole reader removed (`is_readable`
answers true), and only its basicConstraints and keyUsage decode check
removed. The Java answers come from the branch's differential run
(48a6a2a, 3c086fe, `tools/differential/recorded.json` there).

## What OpenSSL judges

| Rule | OpenSSL 4.0.2 | Judged? |
|---|---|---|
| Version 1 to 3 | `d2i_X509` reads `version` as `ASN1_EXP_OPT(X509_CINF, version, ASN1_INTEGER, 0)` (`crypto/x509/x_x509.c:19`); the callback has an `ASN1_OP_D2I_PRE` case and no `D2I_POST` check. `X509_verify_cert` reads the version only inside the `X509_V_FLAG_X509_STRICT` block (`crypto/x509/x509_vfy.c:663`, `700`), which the adapter does not set. `ossl_x509v3_cache_extensions` compares it with v1 to set `EXFLAG_V1` (`crypto/x509/v3_purp.c:491`) | No |
| No extension OID twice | `ossl_x509v3_cache_extensions` (`v3_purp.c:443-733`) decodes the dozen extensions it caches: basicConstraints, proxyCertInfo, keyUsage, extKeyUsage, nsCertType, the subject and authority key identifiers, subjectAltName, nameConstraints, cRLDistributionPoints and the RFC 3779 pair. A repeat or a decode failure of one of those sets `EXFLAG_INVALID` (`:514`, `:550` and the rest); the function then fails (`:727`), `ossl_x509_likely_issued` takes the certificate neither as issuer nor as subject (`:1068-1070`) and `X509_check_ca` answers 0 (`:788`), so a path through it fails | Only for the cached dozen. A repeated Apple marker or an unknown OID is never judged |
| basicConstraints and keyUsage decode | As above: `EXFLAG_INVALID`, then a failed path | On a path, as `UNTRUSTED_CHAIN`; never for a certificate off the path |
| Signature bits whole octets | `ASN1_verify` and `ASN1_item_verify_ctx` refuse unused bits (`crypto/asn1/a_verify.c:46`, `129`) | Only when that signature is verified: never for a stranger in a receipt's bag |

| Shared cases failing | 0 of 390 | 7 | 1 |

With the whole reader removed, `transaction/reject-x5c-certificate-version-11`,
`receipt/reject-signer-certificate-version-11` and
`receipt/reject-a-stranger-whose-signature-bit-string-is-unaligned` verify:
refusals turned into `ok`. Four more cases move to `UNTRUSTED_CHAIN`, outside
what their case allows.

Removing only the decode check is the narrowest change the branch tried.
Its production diff against main, the version fix included, is +45 −50
lines in `rust/openssl/src` and `rust/src`, a net −5. It moved the four
intermediate cases, where the core and Java agreed, into divergences (their
`oneOf` already listed `UNTRUSTED_CHAIN`, so only the differential run
showed it), needed `receipt/reject-signer-with-a-corrupt-extension` made
port-defined, and let an `x5c[2]` whose basicConstraints does not decode
verify, a refusal turned into `ok`.

## The version read

The reader compared rust-openssl's `X509Ref::version()`, which casts the
`c_long` from `X509_get_version` to `i32`. On a 64-bit native build a
version `INTEGER` of 2^32 + 2 read as 2 and the minted leaf verified; on
wasm32, where `long` is 32 bits, `ASN1_INTEGER_get` answers -1 and the
module refused it. The core now calls `X509_get_version` and compares the
`long` (`fix(rust): compare the certificate version as openssl's long`,
test `an_x5c_version_past_32_bits_is_invalid_certificate`), so every build
answers `INVALID_CERTIFICATE`, as BouncyCastle refuses the version at parse.

## Divergences found, no code

The branch's review found two inputs that OpenSSL and the core accept and
BouncyCastle refuses at parse. Neither is Apple-signed in that shape, and
the path is signed either way, so both are recorded in R20 with no code:

- a version 1 or 2 certificate that carries extensions ("version 1
  certificate contains extra data");
- an authorityInfoAccess or certificatePolicies extension whose value does
  not decode. OpenSSL does not cache either, and the core asks for no
  policy check.

## Decision

The reader stays (owner, Q57, revised 2026-10-05 on this evidence); the
version read is fixed. Removing it buys a few lines and turns refusals into
`ok` on rules OpenSSL never applies.

**Where this stops holding.** OpenSSL 4.0.2 with the adapter's flags (no
`X509_V_FLAG_X509_STRICT`, no policy check). A later OpenSSL that judges
the version or repeated extensions at parse would change the first two
rows of the first table.
