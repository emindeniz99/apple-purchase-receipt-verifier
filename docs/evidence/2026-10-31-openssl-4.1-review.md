# OpenSSL 4.1.0 against the core's use of 4.0.3

**Question.** Does moving the core from OpenSSL 4.0.3 to 4.1.0 change any
verdict, break the build, or bring a security fix we need? The answer
decides when the core moves (ROADMAP.md, Next).

**Decision fed (owner, 2026-10-31).** Stay on 4.0.x and take its patches
as they come, a security fix without waiting for the cooldown. Revisit
4.1 around 2026-12-01 or at 4.1.1, whichever is later. Move earlier only
if a security fix reaches 4.1 alone.

## Method

Nothing was built or run. Both release tarballs were downloaded from
`https://github.com/openssl/openssl/releases/download/openssl-<v>/` and
hash-checked:

| Version | Released | SHA-256 |
|---|---|---|
| 4.0.3 | 2026-09-29 | the `OPENSSL_SHA256` in `tools/wasm-toolchain.sh` |
| 4.1.0 | 2026-10-23 | `50c17baf54cb008f6ce42d50deb4b28050a1aad711636cabd4b241c7e90cc2fd` |

The functions the core binds were listed from `rust/openssl/src/`. Then
4.1.0's `CHANGES.md` and `NEWS.md` were read, along with the source diff
of every directory those functions reach: `crypto/{x509,cms,pkcs7,asn1,
evp,ec,rsa,bn,sha,objects,pem}`, the providers behind them and the
public headers.

openssl-library.org lists 4.0 as supported until 2027-05-14 and 4.1
until 2027-11-23.

## Results

**Security.** 4.1.0 lists no CVE. It carries the fixes 4.0.3 has.

**The four known issues in the release notes** are all in DTLS and the
DTLS listener (#32878, #33242, #33277, #33278). `no-sock` turns off
`dgram`, which turns off `dtls` and `quic` (4.1.0 `Configure`), so the
module does not compile that code. `libssl.a` is still linked, because
`openssl_sys::init()` calls `OPENSSL_init_ssl` (`rust/openssl/src/lib.rs`).
That call only loads error strings and cipher tables, which 4.1 did not
change.

**Changes on the core's paths:**

1. `crypto/cms/cms_sd.c`, `CMS_SignerInfo_verify`: a signature-algorithm
   OID such as `sha256WithRSAEncryption` used as the `digestAlgorithm`
   is now refused when the SignerInfo has signed attributes. This turns
   an accept into a reject. Genuine Apple receipts carry plain digest
   OIDs. No shared case in `fixtures/cases.json` has this shape, so CI
   would not see it.
2. `v3_purp.c` and `x509_vfy.c` add `X509_V_ERR_DUPLICATE_EXTENSION`
   (104). No verdict changes, because the core drops such a certificate
   before path building.
3. `v3_purp.c` `scan_ext_flags` calls `RAND_bytes_ex` for each extension
   OID that OpenSSL does not know, and every Apple certificate has one.
   `random-get` would then run on RSA paths too. A failing call still
   traps, so the module fails closed. ARCHITECTURE.md's "only for EC
   blinding" would become false.
4. Name constraints: a leaf's CN is no longer checked against DNS
   constraints by default, and an SmtpUTF8Mailbox otherName constraint
   now invalidates the certificate. Apple's chains carry no name
   constraints, so this reaches only caller-supplied roots.
5. `x_pubkey.c` decodes an `rsaesOaep` public key as RSA. Such a
   certificate becomes usable, so the reason the core gives for
   refusing it may change.
6. `obj_xref.txt` adds `dsa_with_SHA384/512` and
   `sha512_224/256WithRSA`, so certificates signed with those
   algorithms now verify.
7. EC refactors: the `EC_POINT_get_affine_coordinates` fast path, the
   point format moving to the group, and `bn_nist.c` macros used on
   linux-generic32. The genuine ES256 fixtures would catch a
   regression here.
8. `EVP_get_digestbynid` became `EVP_MD_fetch` with a cache, and ASN.1
   strings no longer promise a trailing NUL. The core reads lengths, so
   no verdict change is expected.

**Build.**
- No symbol was removed from `libcrypto.num` or `libssl.num`.
- `ASN1_STRING_length` is deprecated but still exported.
- Every option the core passes to `Configure` still exists. 4.1 drops
  `no-ecdsa` and `no-ecdh`, which the core does not pass.
- `linux-generic32` is unchanged.
- The native path needs an `openssl-src` 401.x release: the vendored
  `openssl-sys` requires `openssl-src = "400.0.1"`.
- The new code uses `snprintf` and SipHash, so the module may grow.

## Before the move

1. A shared case for item 1, with any Java divergence recorded in
   DECISIONS.md R20.
2. A trial wasm build with the new pins in `tools/wasm-toolchain.sh`
   (version, URL, SHA-256, `SOURCE_DATE_EPOCH`). Compare module size and
   the corpus.
3. Correct ARCHITECTURE.md's `random-get` line.

## Where this stops holding

The review covers 4.1.0's source as published. It does not cover a later
4.1.x patch, and it did not run the module, so items 1 and 3 to 6 are
read from the code, not measured.
