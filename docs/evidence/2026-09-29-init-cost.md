# What `init` costs (2026-09-29)

**Question.** Does `init` cost more than 10% of a verify call? If it does,
`aprv-server`'s default lifecycle becomes `--lifecycle pool` (DECISIONS.md
R23, R31; MIGRATION.md step 1.7).

**Answer: yes, by a wide margin.** `init` costs 2.3 to 3.7 ms on every host
measured, 135 to 151% of a pooled G5 receipt call and 28 to 30% of a pooled
JWS call. A fresh instance per request costs 2.6 times a pooled call for G5
on Wasmtime, 1.5 times for a JWS. The rule flips the server's default to
`--lifecycle pool`; the fresh lifecycle stays as the flag.

## Method

- `aprv.wasm` 3,013,162 B (sha256 `95117782…049a`), component 3,015,604 B
  (`888ea7a6…d4e1`), built by `rust/bindings/abi/build.sh` from lane/core
  after 245b4e2 with lane D's toolchain (rustc 1.98.1, wasi-sdk 34.0,
  OpenSSL 4.0.2 for wasm32-wasip1). The later commits on the branch do not
  touch `init`'s path or the two calls measured.
- Wasmtime 49.0.1 (Cranelift, the ABI tests' pin), through the ABI tests'
  own hosts: `CoreGuest` (the core module called by hand) and
  `ComponentGuest` (the component through Wasmtime's component runtime, the
  way `aprv-server` binds it). Node 22.22.2, the core module through
  `WebAssembly` and the canonical ABI called by hand, as the trap host does.
- Inputs: the sandbox G5 receipt under the three Apple roots (`init` with
  `{"roots":[]}`), and `fixtures/generated/transaction.jws` under its
  fixture root (`init` with that one root), at 2026-09-29T00:00:00Z.
- Seven runs of 20 iterations each after a warm-up run, one CPU
  (`taskset -c 0`). Each iteration times a fresh instance (instantiate,
  `init`, one call) and one call on a pooled instance. Medians of the seven
  runs' means; the range in brackets.
- The machine was shared: load average 5.1 to 5.9 on 4 CPUs during the runs
  (`results/load.txt`), so absolute times are high; the ratios are the
  finding, and they hold at every run's extremes.

## Results

From [`results/summary.md`](2026-09-29-init-cost/results/summary.md):

| Host | Input | Instantiate | `init` | First call | Pooled call | `init` / pooled call | Fresh request / pooled call |
|---|---|---|---|---|---|---|---|
| Wasmtime, core by hand | G5 | 0.10 ms | 2.79 ms (2.68-3.74) | 2.40 ms | 2.07 ms (1.87-2.95) | 135% | 2.56x |
| Wasmtime, core by hand | JWS | 0.11 ms | 2.32 ms (2.14-3.26) | 9.00 ms | 7.91 ms (7.35-11.02) | 29% | 1.45x |
| Wasmtime, component | G5 | 0.13 ms | 2.54 ms (2.42-3.22) | 2.13 ms | 1.87 ms (1.75-2.36) | 136% | 2.57x |
| Wasmtime, component | JWS | 0.16 ms | 2.47 ms (2.18-2.76) | 9.61 ms | 8.21 ms (7.53-10.17) | 30% | 1.49x |
| Node, core by hand | G5 | 3.15 ms | 3.65 ms (2.61-6.27) | 2.94 ms | 2.42 ms (2.05-3.79) | 151% | 4.02x |
| Node, core by hand | JWS | 3.12 ms | 2.56 ms (2.11-3.16) | 9.22 ms | 9.21 ms (7.08-10.66) | 28% | 1.62x |

- `init` parses the configuration and the roots, and initialises OpenSSL
  for the instance. It costs about the same for three roots and for one,
  so most of it is OpenSSL's own start-up, not the certificates.
- The first call on a fresh instance is another 10 to 20% slower than a
  pooled call (G5 2.40 against 2.07 ms on Wasmtime), most likely state
  that OpenSSL and the core set up on first use (not measured apart). With
  `init`, that is the spike's 1.6 ms "fresh lifecycle" cost
  ([aprv-server §3](2026-09-26-aprv-server.md)), now split in two.
- Instantiating is cheap on Wasmtime (0.10 to 0.16 ms, the module compiled
  once: 12.4 s under this load for the module and the component together,
  `results/wasmtime-compile.txt`). In Node it is 3.1 ms, because V8 copies
  the module's data segments and sets up its tables per instance.

## Verdict for aprv-server (lane B)

`init` exceeds 10% of a call on every host and input, so `aprv-server`'s
default becomes `--lifecycle pool` (R23): a bounded pool of instances, each
`init`ed once and discarded on a trap, with `--lifecycle fresh` kept for
callers who want nothing to cross from one request to the next. Pooling
saves 2.5 to 3 ms per G5 request here, over half of the request's cost.

## Where this stops holding

x86_64 only, on a loaded machine; one CPU. Other hosts (wazero, Endive,
WasmKit, wasmtime-py, the gem, .NET) were not measured here; their G1
hand-backs report `init` of 3 to 81 ms after the first instance, which only
strengthens the verdict. Wasmtime's pooling allocator and snapshotting an
`init`ed instance (Wizer-style) were not tried.
