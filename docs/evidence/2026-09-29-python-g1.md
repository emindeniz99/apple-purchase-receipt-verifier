# The Python package on the release module (G1 re-run)

Question: does the Python host (`python/`, lane C) give the same answers as
the core on the real 0.7 module, and what does start-up, a call and memory
cost now? It feeds the numbers in `python/README.md` and gate G1.

Module: `aprv.wasm`, 3,005,922 B, sha256
`4cbe2b02056afc41c352fbbacdf6b3804f6f081beaaa8e8ff104340e9ed8826e`, the 0.7
core on OpenSSL 4 (lane A2, `lane/core` 05b4ad9). Package: wasmtime-py 49.0.0,
CPython 3.11.15, Linux x86_64 glibc, 4 CPUs. Date: 2026-09-29.

## Answers

- Conformance: `fixtures/cases.json`, 311 of 311 cases pass through the public
  API (`tests/test_conformance.py`), 0 skipped. The full suite is 438 tests
  and 423 subtests, all passing. Nothing about a case was adjusted. One
  harness rule changed: `tests/test_conformance.py` told "refused as base64"
  from "decoded, refused later" by the failure message naming base64, and the
  module refuses the empty receipt by name (`receipt is empty`, reason
  MALFORMED) before it reaches the decoder, as the case describes ("each port
  refuses it before decoding"). The harness now takes the reason alone for the
  empty text.
- The 0.6 stand-in's list of 217 expected differences is gone, with its
  loader, the `standin_differs` marker and the recording script.
- Corpus parity through `_host.Pool`, byte for byte against the module's own
  rows (`same.py`): algorithms 22 of 22, cases 153 of 153, hostile 811 of 811,
  substrate 193 of 193, fuzz 5,000 of 5,000: 6,179 of 6,179 identical, 0
  traps. The run takes about 32 s (fuzz 21 s).

## Cost

The runner was shared and busy for every measurement (load average 8 to 20 on
4 CPUs), so wall times are upper bounds. To have something comparable, the
stand-in (sha256 `da786ac8...fdb68`, 2,967,116 B) was measured in the same
minutes with the same scripts.

Start-up, `measure.py` (3 runs; fresh process each; median, minimum in
brackets), first `Verifier(Config.defaults())`:

| | cache off, wall | cache off, CPU | cache hit, wall | cache hit, CPU |
|---|---|---|---|---|
| release, 4 CPUs | 7.8 s (6.9) | 5.4 s (5.2) | 116 ms (106) | 106 ms (80) |
| stand-in, 4 CPUs | 7.6 s (6.2) | 5.5 s (5.3) | 145 ms (138) | 83 ms (81) |
| release, 1 CPU | 8.1 s (6.2) | 5.6 s (5.0) | 110 ms (105) | 78 ms (73) |
| stand-in, 1 CPU | 5.5 s (5.0) | 4.9 s (4.5) | 99 ms (77) | 76 ms (75) |

A first run into an empty cache directory costs the same as no cache (the
compile), and a hit costs about 0.1 s. The release module compiles at the
same cost as the stand-in. On an idle machine the earlier module measured 934
ms on 4 CPUs and 2,923 ms on one (`2026-09-27-python-runtime-options.md`); the
release module was not measured idle, so the README's "1 to 3 s idle" is that
figure carried over, supported only by the equal-cost comparison above.

A second `Verifier` in the same process (instance and `init`, no compile): 3.4
ms median (2.9 min) on the release module, 4.9 ms (3.2) on the stand-in. This
is not the 0.4 to 0.6 ms the README carried from the earlier spike, and the
stand-in shows the same 3 to 5 ms in the same minutes, so the module is not
the cause; I did not find out what differs in how the earlier figure was taken.

Peak resident memory after the first `Verifier`: 150 MB after a compile, 54 MB
after a cache hit, and unchanged after 300 more calls (the stand-in: 149 MB and
54 MB). `tests/test_abi.py` also pins that memory does not grow with calls.

Per call, `calls.py` (CPU time of one thread, median of samples of 10 calls,
two runs):

| input | release | stand-in |
|---|---|---|
| receipt-sandbox-g5 (2 purchases) | 2.2 and 3.0 ms | 2.4 and 2.6 ms |
| receipt-sandbox-legacy (187 purchases) | 18.2 and 19.4 ms | 14.6 and 12.9 ms |
| transaction.jws | 7.9 and 8.0 ms | 12.3 and 13.6 ms |

`bench/bench.py` (wall clock, same runner): verifierBase64 4.0 ms (g5) and
30 ms (legacy), endpointJson 3.8 and 15 ms, rejectTamperedSignature 2.8 ms for
both. The stand-in row for the JWS answers 0.6's object payload, which the
0.7 wrapper reports as an internal error, so its time is not that of a
verification and is shown only for scale.

Threads and processes (`throughput.py`): 1, 2 and 4 threads gave 220 to 231,
258 to 377 and 310 to 329 receipts per second; 1, 2 and 4 processes gave 309 to
376, 261 to 312 and 193 to 270. The processes column is meaningless here (two
processes were slower than one) because the runner had no idle CPU. The README
keeps the idle-machine figures from the earlier module (583, 946, 566 threads;
595, 1,123, 2,259 processes); they were not reproduced.

## Where this stops holding

One machine, busy, CPython 3.11 only, glibc only. Not run: musl, aarch64,
macOS, Windows, idle-machine timings of the release module, throughput
scaling. Rerun `measure.py`, `calls.py` and `throughput.py` on a quiet
machine before quoting a figure as a limit.

## Reproduce

`$SCRATCH` is any directory outside the repository, `$G1` the core lane's
hand-over directory (`aprv.wasm`, `calls/`, `rows/`, `same.py`).

```sh
cd python
PYTHON=$VENV/bin/python tools/g1.sh $G1          # answers: suite and corpora
$VENV/bin/python ../docs/evidence/2026-09-29-python-g1/measure.py $SCRATCH/cache 3
$VENV/bin/python ../docs/evidence/2026-09-29-python-g1/calls.py
$VENV/bin/python ../docs/evidence/2026-09-29-python-g1/throughput.py 4
```

`tools/g1.sh` copies the module into the git-ignored package path and rewrites
the tracked `aprv.wasm.sha256`; the module itself is never committed.
