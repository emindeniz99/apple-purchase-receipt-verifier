# 0.7 API design

Owner decisions from the 2026-09-26/27 design sessions, revised after a
review on 2026-09-27. Java is built first and serves as the reference; the
other eight ports follow the same shape, and 0.7 ships all nine together.
0.7 removes the 0.6 API: breaking changes are allowed before 1.0.

## Principles

1. **A verifier, not business logic.** The library answers one question:
   did Apple sign this data, under a pinned Apple root? If so, it returns
   the data.
2. **No policy.** Bundle id, environment, product id, device binding,
   refunds and idempotency are the caller's decisions. The library takes no
   parameter for any of them.
3. **Only the endpoint imitates Apple.** `verifyReceiptEndpoint` returns
   the response Apple's verifyReceipt would return, identical where the
   receipt allows it. COMPARISON.md lists what a receipt cannot carry
   (`latest_receipt_info`, `pending_renewal_info`, `latest_receipt`). The
   other two methods return our own types.
4. **Idiomatic per language, identical in meaning.** Every port exposes the
   same three methods, the same `Reason` values, the same field names in
   each language's casing, and the same JSON bytes. Error wrappers, clock
   types and data classes follow each language's conventions, within each
   port's existing version floor.

## Setup

```java
public final class Config {                     // immutable
    public static Config defaults();            // Apple's pinned roots + Clock.systemUTC()
    public static Builder builder();            // roots(...), clock(...)
    public Set<X509Certificate> roots();        // an unmodifiable copy
    public Clock clock();
}

public interface Verifier {                     // immutable, thread-safe, never throws
    static Verifier create(Config config);
    VerificationResult<ReceiptPayload> verifyReceipt(String base64);
    VerificationResult<JsonPayload>    verifySignedData(String jws);
    String verifyReceiptEndpoint(Environment environment, String requestJson);
}

public final class Version {
    public static final String CURRENT = "0.7.0";
}
```

- **Roots** default to the three bundled, pinned Apple roots. Tests
  replace them with their own.
- **Clock** answers "what time is it now?" and nothing else. The library
  reads it in two places: the chain check when the receipt or JWS carries
  no signing date, and `request_date` in the endpoint response. Java takes
  a `java.time.Clock` and reads `clock.millis()`. A caller-supplied clock
  must be safe to call from several threads.
- **Startup failures.** `Config.defaults()` loads the bundled roots and
  throws `IllegalStateException` when they are missing or fail their
  pinned fingerprints. `Verifier.create` throws `IllegalArgumentException`
  for an empty root set, because a verifier with no roots would answer
  `UNTRUSTED_CHAIN` to everything and nobody would notice until
  production. Both happen once, at startup.
- **The verify methods never throw for any input.** They catch unexpected
  runtime exceptions and report them as `INTERNAL_ERROR`. Only JVM errors
  such as `OutOfMemoryError` escape.
- **Null arguments.** A `null` or empty input string (`base64`, `jws`,
  `requestJson`) is input and fails as `MALFORMED`, as 0.6 does. A `null`
  `Environment` or `Config` is a programming error, never something a
  receipt can cause, and throws `NullPointerException`. This is the one
  exception to never-throw, and every port applies the same split in its
  own idiom (Rust and Swift cannot pass null; Go returns an error for a
  nil config).
- Callers mock `Verifier` in their own tests; it is an interface for that
  reason.
- **Java 8 stays the floor,** so the data types below are immutable final
  classes with constructors, getters, `equals`, `hashCode` and `toString`,
  not records.
- **`Version.CURRENT` is bumped by release-please.** It joins the
  `extra-files` list in `release-please-config.json` in the same commit
  that adds it, so 0.7.1 does not report "0.7.0". The "one version, N
  files" note in CLAUDE.md changes with it.
- **The implementation stops being public.** In 0.6 the `internal`
  package is public because `receipt/` and `jws/` both reach the shared
  BouncyCastle provider from different packages, and Java 8 has no
  modules to hide it. 0.7 has one `Verifier` implementation, so the whole
  implementation moves into one package as package-private classes and
  only the API types are public. No jar tricks, works on Java 8. A
  multi-release jar with a `module-info` for Java 9 and later would only
  hide the same classes from modular consumers, not from the classpath
  apps most callers run, and needs a second compile pass; it stays in
  ROADMAP.md. The `Automatic-Module-Name` manifest entry stays.

## Result

```java
public final class VerificationResult<T> {
    boolean verified();
    @Nullable T payload();         // set only when verified
    @Nullable Failure failure();   // set only when not verified
}

public final class Failure {
    Reason reason();
    String message();              // safe to log, not meant to be parsed
    @Nullable Throwable cause();   // the inner exception, when there is one
}

public enum Reason {
    MALFORMED,            // base64, ASN.1, CMS or JWS structure is broken
    TOO_LARGE,            // input over a fixed cap (see Bounds)
    INVALID_SIGNATURE,    // the signature does not match the content
    UNTRUSTED_CHAIN,      // the chain does not reach a pinned root
    INVALID_CERTIFICATE,  // unreadable certificate, or outside its validity
    INVALID_CERTIFICATE_PURPOSE, // a valid Apple certificate of the wrong kind: marker OID missing
    UNREADABLE_PAYLOAD,   // Apple signed it, but the content does not parse
    INTERNAL_ERROR        // the library failed; alert, do not retry
}
```

- `UNREADABLE_PAYLOAD` and `INTERNAL_ERROR` replace the single 0.6
  `INTERNAL_ERROR`. The first means the signature and chain verified and
  the payload bytes are Apple's, but the parser cannot read them. The
  second means the library itself broke before it could decide. Both are
  deterministic for the same input; neither is worth a retry.
- `message` never embeds raw input. Control characters and bidi controls
  in anything quoted from the input are neutralised, as `SafeText` does in
  0.6, so a message can go into a log line as is. Match on `reason()`;
  the text may change between releases.
- `cause` carries the parser or provider exception behind
  `UNREADABLE_PAYLOAD` and `INTERNAL_ERROR`, so an operator can see why
  Apple-signed content did not parse. Other ports expose it the way their
  error types do (Rust `source()`, Python `__cause__`, .NET
  `InnerException`).

### Which failure a parse problem gets

Both formats read part of the payload before the signature is checked:
the receipt's creation date (attribute 12) and the JWS's `signedDate`
pick the instant for the chain check. That reading happens under the size
and depth bounds below, on input nobody has vouched for yet, so a parse
failure at that point must not be reported before the signature has been
checked. The rule, the same in every port:

- A broken outer structure fails as `MALFORMED` before any cryptography:
  bad base64, a CMS envelope that does not decode, a JWS without three
  segments or with bad base64url.
- Content inside a well-formed envelope that does not parse (an attribute
  set that is not valid ASN.1, a JWS payload that is not a JSON object)
  is carried past the chain and signature checks, with the clock standing
  in for the missing date. If the signature fails, the result is
  `INVALID_SIGNATURE`; if it verifies, `UNREADABLE_PAYLOAD`.

Two shared cases pin this, one per format.

## Bounds

All unchanged from 0.6 except the signer cap, all pinned by shared cases,
none configurable:

| Bound | Value | Failure |
|---|---|---|
| Receipt base64, UTF-8 bytes | 3,145,728 | `TOO_LARGE` |
| Endpoint request body, UTF-8 bytes | 3,145,728 | `TOO_LARGE` (status 21002) |
| JWS, UTF-8 bytes | 262,144 | `TOO_LARGE` |
| JSON nesting depth | 64 | `MALFORMED` |
| Certificates embedded in a receipt | 10 | `MALFORMED` |
| Chain length, leaf to root | 6 | `UNTRUSTED_CHAIN` |
| SignerInfos in a receipt | 4 (new) | `MALFORMED` |

## 1. `verifyReceipt(base64)`: legacy receipt

The library checks, in order: strict base64, the CMS envelope, the chain
to a pinned root walked top-down (#161), Apple's marker OIDs on both the
leaf (receipt signing) and the WWDR intermediate, the signature, and
certificate validity at the receipt's creation date. It then decodes the
payload. The intermediate marker check is new in 0.7 (owner, 2026-09-27):
it brings the receipt path level with the JWS path, which has always
checked both, and a shared case with an intermediate lacking the marker
pins it as `INVALID_CERTIFICATE_PURPOSE`. Every genuine Apple chain
carries the marker, so no real receipt is affected.

**What verification reads.** From the envelope: the certificates, the
SignerInfos, the signature and digest, and the content type. From the
payload it reads one attribute, type 12 (receipt creation date), to pick
the instant for the chain check. The clock stands in when that attribute
is missing or does not parse. Every other attribute is decoded for the
caller only.

**Several SignerInfos.** The library accepts the receipt when at least one
SignerInfo verifies under a pinned chain. All signers sign the same
content, so an extra signer cannot change what Apple signed. This keeps a
future dual-signed receipt working. The cap is four SignerInfos; a fifth
fails as `MALFORMED` before any signature is checked. Two shared cases pin
this in every port: one valid Apple signer beside one broken signer
verifies, and two broken signers fail as `INVALID_SIGNATURE`. Ports whose
CMS library checks every signer by default (.NET's `SignedCms`, PHP's
`openssl_pkcs7_verify`) must iterate the signers themselves to match.

```java
public final class ReceiptPayload {
    @Nullable String receiptType();                // 0
    @Nullable Long   appItemId();                  // 1
    @Nullable String bundleId();                   // 2
    byte @Nullable [] bundleIdBytes();             // 2, the value octets as they sit in the receipt
    @Nullable String applicationVersion();         // 3
    byte @Nullable [] opaqueValue();               // 4
    byte @Nullable [] sha1Hash();                  // 5
    @Nullable Long   receiptCreationDateMs();      // 12
    @Nullable Long   downloadId();                 // 15
    @Nullable Long   versionExternalIdentifier();  // 16
    List<InAppPurchase> inApp();                   // 17
    @Nullable Long   originalPurchaseDateMs();     // 18
    @Nullable String originalApplicationVersion(); // 19
    @Nullable Long   expirationDateMs();           // 21
    Map<Integer, List<byte[]>> unknownAttributes();
    String toJson();
}

public final class InAppPurchase {
    @Nullable Long    quantity();                  // 1701
    @Nullable String  productId();                 // 1702
    @Nullable String  transactionId();             // 1703
    @Nullable Long    purchaseDateMs();            // 1704
    @Nullable String  originalTransactionId();     // 1705
    @Nullable Long    originalPurchaseDateMs();    // 1706
    @Nullable Long    expiresDateMs();             // 1708
    @Nullable Long    webOrderLineItemId();        // 1711
    @Nullable Long    cancellationDateMs();        // 1712
    @Nullable Boolean isTrialPeriod();             // 1713
    @Nullable Boolean isInIntroOfferPeriod();      // 1719
    Map<Integer, List<byte[]>> unknownAttributes();
}
```

Decode rules:

- Field names are Apple's own words from the verifyReceipt response
  (`application_version`, `in_app`), so a caller reading our JSON, the
  Java getters and Apple's documentation sees one vocabulary. Each port
  spells them in its own casing.
- A missing attribute decodes to `null`. The library invents no values.
- Dates are epoch milliseconds, UTC, with an `Ms` suffix. Receipt dates
  carry whole seconds, so the last three digits are always `000`. A date
  attribute that does not parse decodes to `null`.
- The trial and intro flags are `Boolean`: 0 is `false`, any other value
  is `true`.
- `bundleIdBytes`, `opaqueValue` and `sha1Hash` are the attribute value
  octets exactly as they sit in the receipt. Apple's device-hash formula
  hashes those three plus the device identifier, so a caller can compute
  it from these fields alone.
- `unknownAttributes` maps an attribute type to its raw value octets, in
  receipt order. The attribute's `version` integer is not kept.
- Public constructors let callers build payloads by hand in their tests.

### Our JSON (`ReceiptPayload.toJson()`)

For logging and storage. Keys, in this order:

| Java | JSON key | JSON type |
|---|---|---|
| `receiptType` | `receipt_type` | string |
| `appItemId` | `app_item_id` | string |
| `bundleId` | `bundle_id` | string |
| `bundleIdBytes` | `bundle_id_bytes` | base64 string |
| `applicationVersion` | `application_version` | string |
| `opaqueValue` | `opaque_value` | base64 string |
| `sha1Hash` | `sha1_hash` | base64 string |
| `receiptCreationDateMs` | `receipt_creation_date_ms` | number |
| `downloadId` | `download_id` | string |
| `versionExternalIdentifier` | `version_external_identifier` | string |
| `inApp` | `in_app` | array |
| `originalPurchaseDateMs` | `original_purchase_date_ms` | number |
| `originalApplicationVersion` | `original_application_version` | string |
| `expirationDateMs` | `expiration_date_ms` | number |
| `unknownAttributes` | `unknown_attributes` | object: `{"13": ["<base64>", ...]}` |

Inside `in_app`, in this order: `quantity` (number), `product_id`,
`transaction_id`, `purchase_date_ms`, `original_transaction_id`,
`original_purchase_date_ms`, `expires_date_ms`, `web_order_line_item_id`
(string), `cancellation_date_ms`, `is_trial_period` (boolean),
`is_in_intro_offer_period` (boolean), `unknown_attributes`.

Rules:

- 64-bit ids (`app_item_id`, `download_id`, `version_external_identifier`,
  `web_order_line_item_id`) are JSON strings. Genuine receipts carry
  18-digit `download_id` values, above 2^53, which JavaScript would round.
  Epoch milliseconds stay below 2^53 until about the year 287,000, so
  dates are numbers.
- A missing field is written as `null`, not omitted.
- Bytes are standard base64 with padding.
- **Canonical form, so nine ports produce the same bytes:** no
  whitespace, keys in the order above, UTF-8, only the escapes JSON
  requires (`"`, `\`, control characters as `\uXXXX`), no escaping of
  `/`, and non-ASCII characters written raw rather than as `\uXXXX`.
  Go's and Python's default encoders violate two of these (HTML-safe
  escaping, `ensure_ascii`); each port configures its encoder or writes
  the few lines itself. A shared vector file pins the output for the
  public fixtures, including one with a non-ASCII product id.

## 2. `verifySignedData(jws)`: StoreKit 2 JWS

The library checks the compact JWS structure, `alg` equal to `ES256`, the
`x5c` chain to a pinned root with Apple's marker OIDs on the leaf and the
intermediate, the signature, and certificate validity at the payload's
`signedDate` (the clock when it is missing). It parses the payload only to
read `signedDate` and to confirm the payload is a JSON object, under the
depth and size bounds.

```java
public final class JsonPayload {
    String json();   // the verified payload, unchanged
}
```

One method covers every Apple JWS: transactions, renewal info, app
transactions and App Store Server Notifications V2. A notification nests
more JWS inside its payload. Apple POSTs `{"signedPayload": "<JWS>"}`;
the verified payload holds `data.signedTransactionInfo` and
`data.signedRenewalInfo`, each a JWS of its own, and the caller passes
each one to `verifySignedData` again. A `TEST` notification carries
neither (checked against Apple's `testNotification` fixture in
`fixtures/apple-official/mock_signed_data/`). The README shows the loop.

The header (`alg`, `x5c`) is not returned, as the receipt side returns no
algorithm or certificates. Callers parse `json()` with their own JSON
library. Apple's claims are epoch milliseconds already (`purchaseDate`,
`expiresDate`, `signedDate`). A JWS has no expiry of its own; comparing
`expiresDate` with the caller's clock is business logic.

## 3. `verifyReceiptEndpoint(environment, requestJson)`

Input is the verifyReceipt request body, `{"receipt-data": "...", ...}`.
Output is the response JSON Apple would return, as a `String`. The method
runs `verifyReceipt` and renders the result in Apple's format.

- `environment` is `PRODUCTION` or `SANDBOX`, Apple's two URLs.
- A sandbox receipt on a `PRODUCTION` endpoint returns 21007. The caller
  calls again with `SANDBOX`, as with Apple; the second call is offline.
  A receipt whose `receipt_type` is missing or unknown counts as
  non-production, as in 0.6: 21007 on `PRODUCTION`, status 0 on
  `SANDBOX`.
- `web_order_line_item_id` is omitted when attribute 1711 is 0, as Apple
  omits it for consumables.
- `request_date` comes from the config clock.
- `password` and `exclude-old-transactions` are read and ignored, as in
  0.6 (COMPARISON.md). Trailing tokens after the JSON object follow
  whatever Apple's endpoint does with them, measured first (ROADMAP.md).

Status from `Reason`, the same table in every port:

| Verification outcome | Status |
|---|---|
| verified, environment matches | 0 |
| verified, sandbox receipt on `PRODUCTION` | 21007 |
| verified, production receipt on `SANDBOX` | 21008 |
| `MALFORMED`, `TOO_LARGE` | 21002 |
| `INVALID_SIGNATURE`, `UNTRUSTED_CHAIN`, `INVALID_CERTIFICATE`, `INVALID_CERTIFICATE_PURPOSE` | 21003 |
| `UNREADABLE_PAYLOAD`, `INTERNAL_ERROR` | 21009 |

Both 21009 cases are deterministic for the same input, so the README keeps
telling callers to alert on 21009 rather than retry. Apple's 21005 and
21100 to 21199 mean Apple's own servers failed and invite a retry; the
endpoint never returns them.

## Helpers

- `Environment` has two values, `PRODUCTION` and `SANDBOX`. The 0.6
  `XCODE` and `LOCAL_TESTING` values go: they only ever named JWS
  `environment` strings, such payloads are not Apple-signed and fail the
  chain check regardless, and the caller now reads that string from the
  JSON. Dropping them also removes the `IllegalArgumentException` the 0.6
  endpoint threw for them.
- `Environment.fromReceiptType(String)` maps Apple's `receipt_type`:
  `Production` and `ProductionVPP` to `PRODUCTION`, `ProductionSandbox` and
  `ProductionVPPSandbox` to `SANDBOX`, anything else to `null`. It states
  what Apple's value means and decides nothing. The endpoint uses the same
  rule for 21007 and 21008.
- `Environment.fromJwsEnvironment(String)` maps a JWS `environment` claim
  the same way: `Production` and `Sandbox`, anything else to `null`.
- `Version.CURRENT`, for startup logs.
- `AppleStatus`, named constants for every status code Apple documents
  for verifyReceipt (21000 to 21010 and the 21100 to 21199 range), with
  the Javadoc naming which of them this endpoint can return, so callers
  do not write `21007` by hand. The 0.6 `STATUS_*` constants on
  `VerifyReceiptEndpoint` go away with that class.

## Removed in 0.7

- `ReceiptVerifier`, `JwsVerifier`, `VerifyReceiptEndpoint`,
  `VerifyReceiptResult` and the typed JWS models (`TransactionPayload`,
  `AppTransactionPayload` and the rest). No deprecation period.
- The bundle id, environment and `deviceGuid` parameters. A caller who
  wants the device-hash check computes SHA-1 over device id, `opaqueValue`
  and `bundleIdBytes` and compares it with `sha1Hash`; the README shows it.
- **The policy cases in `fixtures/cases.json` become positive cases.**
  No case is deleted. The 8 cases whose reason is `WRONG_BUNDLE_ID`,
  `WRONG_ENVIRONMENT`, `WRONG_APP_APPLE_ID` or `DEVICE_HASH_MISMATCH`
  keep their inputs (Apple's own `wrongBundleId` mock, a genuine sandbox
  G5 receipt, a bundle id that differs only by letter case) and flip to
  "verifies, and the payload shows this value": the other app's bundle
  id, `Sandbox`, the other `appAppleId`, or the raw `opaqueValue`,
  `sha1Hash` and `bundleIdBytes` the device-hash example hashes. That
  pins in every port that the library returns the data instead of
  judging it. The `bundleId`, `acceptedEnvironments`, `appAppleId` and
  `deviceGuidHex` keys in case configs (139 and 51 for the first two)
  leave the schema in the same commit, since no port reads them. The
  `Reason` set in the schema changes to the one above, in this mapping:
  `INVALID_CHAIN` becomes `UNTRUSTED_CHAIN`; `INVALID_RECEIPT_FORMAT`,
  `INVALID_JWS_FORMAT` and `MALFORMED_REQUEST` fold into `MALFORMED`;
  `REQUEST_TOO_LARGE` becomes `TOO_LARGE`; `INVALID_CERTIFICATE`,
  `INVALID_CERTIFICATE_PURPOSE` and `INVALID_SIGNATURE` keep their names;
  and the 12 `INTERNAL_ERROR` cases are re-labelled `UNREADABLE_PAYLOAD`
  or `INTERNAL_ERROR` one by one.
- The `jackson-databind` and `jackson-annotations` dependencies. Java keeps
  `jackson-core` for its streaming parser and generator, which read the JWS,
  read the endpoint request and write both JSON outputs. `jackson-core` 2
  and Jackson 3 live in different packages and coexist.

## The other ports

Each port uses what its published floor has. Two floors move in 0.7,
both past the vendor's end of life (SUPPORT-MATRIX.md) and both for a
language feature the port needs, which is the matrix's rule for moving
one: Ruby from 3.1 to 3.3 for `Data`, PHP from 8.1 to 8.2 for
`readonly class`. SUPPORT-MATRIX.md and the two manifests change in the
commits that land those ports.

| Port | Floor | Result form | Clock | Data types | 64-bit ids |
|---|---|---|---|---|---|
| Java | 8 | `VerificationResult` | `java.time.Clock` | final classes | `Long` |
| Rust | 1.85 | `Result<Payload, Failure>` | closure returning epoch ms | structs, `Option` | `i64` |
| Go | 1.22 | `(payload, error)` | `func() int64` | structs | `int64` |
| Swift | 6.1 | `Result<Payload, Failure>` | closure | structs | `Int64` |
| .NET | netstandard2.0 | result object | `Func<long>` | records | `long` |
| PHP | 8.2 (was 8.1) | result object | PSR-20 `ClockInterface` | `readonly class` | `int` |
| Python | 3.10 | result object | callable | frozen dataclasses | `int` |
| Ruby | 3.3 (was 3.1) | result object | proc | `Data` | `Integer` |
| Node | 20 | result object | `() => number` | readonly interfaces | **`string`** |

- Node cannot hold an 18-digit id in a `number`, so its 64-bit ids are
  strings, matching the JSON.
- Rust ids are `i64`, not `u64`: an ASN.1 INTEGER in hostile input can be
  negative, and the decoder reports what is there.
- .NET takes `Func<long>` rather than `TimeProvider`, which needs .NET 8
  or an extra package on netstandard2.0; the netstandard2.0 floor stays
  because it is what keeps .NET Framework consumers.
- Java 8 stays for the same reason: it is an advertised floor. Watch item
  for 1.0: Temurin's Java 8 builds end in late 2026, and the
  `java-runtime-8` CI leg runs on them.
- Go's `Failure` implements `error` and exposes `Reason`; Swift's
  conforms to `Error`; Rust's implements `std::error::Error` with
  `source()`.
- The Rust C ABI in `rust/ffi/` changes with the Rust port. Its
  interchange format is already JSON, so its receipt result is exactly
  `ReceiptPayload.toJson()`.

If a shared Rust core compiled to WebAssembly ever sits under the ports,
the core takes `now_ms` as a plain argument on each call and never calls
back into the host. Each port's wrapper reads its clock once per call and
passes the value in. The public API above stays the same.

## Testing

- **The caller's logic:** mock `Verifier` and build `ReceiptPayload` by
  hand.
- **The caller's wiring:** a sandbox receipt from the caller's own app. It
  keeps verifying, because the chain is judged at the receipt's creation
  date.
- **Synthetic receipts end to end:** the internal `TestPki` signer ships
  as a Maven test-jar classifier at the end of 0.7, restricted to
  `TestPki` and moved off `jackson-databind`.
- **New shared cases for 0.7:** the two signer cases, the two
  parse-after-signature cases, the intermediate-marker case, the JSON
  vector with a non-ASCII product id, and the eight flipped policy cases.

## Release

- Java lands on `main` first, as the reference; the other ports follow on
  `main` one by one; one `v0.7.0` tag publishes all of them.
- crates.io, RubyGems and NuGet are not bootstrapped as of 0.6.0
  (BOOTSTRAP.md). Unless that happens before the tag, 0.7 reaches six
  registries, as 0.6 did.

## Room for revocation checks later

Revocation checks are deferred (ROADMAP.md), but 0.7 keeps the door open
so adding them later breaks nothing:

- `Config` is a class with a builder, so an optional
  `revocations(...)` setting can join it without changing any existing
  call. The `Verifier` stays immutable; a revocation source it references
  may update itself on the host's schedule.
- A revoked certificate will fail as `INVALID_CERTIFICATE`, with
  "revoked" in the message. No new `Reason` value is needed; adding one
  would be a breaking change across all nine ports.

## Deferred

Recorded in ROADMAP.md: a cache of successful signature checks, removing
the second signature check that BouncyCastle's PKIX repeats after the
top-down walk, online revocation checks, and a shared Rust/WebAssembly
core.

## Dropped

- `decodeUnverified()`. `openssl` already opens a receipt without
  verifying it, and a public unverified parser adds attack surface.
- Per-call time parameters. The config clock covers the chain fallback and
  `request_date`.
- A per-call Jackson `Map` of JWS claims. Callers parse `json()`.
- A `byte[]` DER overload of `verifyReceipt`. 0.6 had
  `verifyReceiptCore(byte[])`; a caller holding DER bytes base64-encodes
  them. An overload can be added later without breaking anything.
