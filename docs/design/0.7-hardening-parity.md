# 0.7 hardening parity

Before 0.6.0 the Java port had a production review, and several fixes from it
landed in Java only. This document tracks carrying each of them to the other
eight ports as part of their 0.7 rewrite. Delete it once every item below is
resolved.

Status values in the tables:

- **has**: the port already does this; the cited line is the evidence.
- **MISSING**: the port must add it in its 0.7 rewrite.
- **change**: the port does something the owner decided against; align it.
- **n/a**: the Java fix addressed something the port cannot hit; the reason is given.
- **untested**: the behaviour is not pinned by any test in the port.

Rust is being rewritten in the 0.7 work at the time of writing, so every Rust
cell reads "in progress in the 0.7 work". File references are relative to the
port's directory and were read on `feat/0.7-verifier-api`.

## Decisions (owner, 2026-09-27)

| Question | Decision |
|---|---|
| Q13 Release vehicle | The fixes land in each port's 0.7 rewrite. There is no separate 0.6.x release. |
| Q14 Certificate signature algorithms in the chain | Accept whatever the port's library verifies under the pinned chain, as Java does. No extra allowlist. Go and .NET remove theirs. |
| Q15 MD5 digest for a receipt signer | Accept it, as Java does since #160: any digest the signer's pinned chain signed. RSA binds the digest algorithm inside the signature; ECDSA does not, but Apple signs with RSA and a relabelling attack needs an Apple signature plus a collision. |
| Q16 Genuine receipt padded with stranger certificates | It verifies, as in Java. The certificate bag is not signed, so a certificate no pinned root vouches for is ignored rather than fatal. |
| Q17 Host crypto policy independence (RHEL 9 refusing SHA-1) | Stays on the ROADMAP, after 0.7. Listed below for completeness only. |

## The Java-only changes

| # | Change | Java PR and commits |
|---|---|---|
| 1 | **Top-down chain check.** Verify certificate signatures only with keys already vouched for by a pinned root, walking down from the roots; decode a certificate's key only after that. On the JWS path, check `x5c[1]` against the pinned roots before checking `x5c[0]` against `x5c[1]`. | #161, merge 6881b68, fix bd52b42 |
| 2 | **Stranger certificates are ignored.** An embedded certificate that no pinned root vouches for never reaches the path builder, so a genuine receipt carrying one still verifies (Q16). | #161, bd52b42 |
| 3 | **Any receipt signer algorithm.** The signer must chain to a pinned root, carry Apple's receipt-signing marker and its signature must verify; its key type, digest and signature algorithm are not restricted. | #160, merge 918a0eb, feat 2ba48bc |
| 4 | **Contain unexpected errors before the signature.** Any unexpected runtime error before the signature has verified is reported as the format reason (MALFORMED in 0.7), never INTERNAL_ERROR, because the input is still unauthenticated. | #153, merge b998ae5, fix bcdd3cd, docs b99339b |
| 5 | **One verdict for an unreadable certificate.** An unreadable signer is INVALID_CERTIFICATE; any other unreadable embedded entry is a format failure; a broken signer outranks a broken stranger. | #153, b998ae5, a2bac88 |
| 6 | **Log-safe messages.** Input quoted in a message, and third-party exception text, has control characters (C0, C1, DEL, U+2028, U+2029) removed and is length-limited; catch-all guards name only the exception class. | #157, merge e5fc364, fixes e3785f9 and 9972f25 |
| 7 | **No raw library cause chain in the exposed cause.** The failure cause handed to callers carries sanitised text only, because library messages can quote certificate names from the input. | #157, e5fc364, 6150da0 |
| 8 | **Parse failure after the signature is internal.** A failure to read claims after the signature has verified is INTERNAL_ERROR (UNREADABLE_PAYLOAD in 0.7), not a format error. | #157, e5fc364, 2334793 |
| 9 | **Endpoint keeps the failure cause.** The endpoint keeps the verification error as the failure cause for every failure. Superseded by the 0.7 `cause` rule in docs/design/0.7-api.md, so it is tracked there, not here. | #157, e5fc364, 7e96cca |
| 10 | **Apple parity tests.** Pins four behaviours: a genuine receipt with one content byte changed is INVALID_SIGNATURE; a four-segment JWS is a format error; the pre-2018 purchase-info receipt is a format error (21002); Apple's real production `x5c` reaches the signature check, and fails the chain outside its validity window. | #158, merge 77c8c65, tests 2438b50, 63588af, 346ac07, 6611ff2 |
| 11 | **Signature algorithm field checked with the digest.** Java's receipt allowlist also covered the SignerInfo signature algorithm. Superseded by change 3 and specific to Java's library. | #158, 77c8c65, db68e13 |
| 12 | **Host crypto policy independence.** All Java cryptography runs on a pinned provider, so a host policy that refuses SHA-1 does not change a verdict (Q17: after 0.7). | #152, merge 072b543, fix dae21b2, CI 563c9e4 |
| 13 | **Library errors from lazily decoded fields.** Unchecked errors from lazily decoded certificate fields become verdicts. Specific to Java's library. | #152, 072b543, ccdc172 |
| 14 | **Raw request body in framework examples.** Documentation: a framework that parses `application/x-www-form-urlencoded` bodies rebuilds the request, so the example reads the raw body. | #159, merge 325158e, docs 7ee6f1f |
| 15 | **Strict string types and strict `x5c` base64.** Only UTF8String and IA5String receipt strings; `x5c` entries as strict standard base64. The other ports already did both, and shared vectors pin them. | #142, merge 89afd21, fixes 83b09d4 and a852b10 |

## Per-port status

### Change 1: top-down chain check

Every port below checks a certificate's signature with the key of the next
certificate up, before a pinned root has vouched for that key.

| Port | Status | Evidence |
|---|---|---|
| go | MISSING | JWS `internal/chain/chain.go:123` runs before the root check at `:126`; receipt walk `:178` |
| swift | MISSING | receipt walk `Sources/ApplePurchaseReceiptVerifier/ReceiptVerifier.swift:267-277`; JWS `JwsVerifier.swift:359` hands the pair to swift-certificates' `Verifier`, which checks bottom-up |
| dotnet | MISSING | `src/ApplePurchaseReceiptVerifier/Internal/CertificateChain.cs:74` (JWS), `:131` (receipt) |
| php | MISSING | `src/Internal/ChainValidator.php:58` (JWS), `:100` (receipt) |
| python | MISSING | `apple_purchase_receipt_verifier/_chain.py:106` (JWS), `:128` (receipt) |
| ruby | MISSING | `lib/apple_purchase_receipt_verifier/chain.rb:98` (JWS), `:123` (receipt) |
| node | MISSING | `src/chain.ts:43` (JWS), `:75` (receipt); web build `src/web/chain.ts:133`, `:171` |
| rust | in progress in the 0.7 work | |

Keys are also decoded before trust in several ports (dotnet
`Jws/JwsVerifier.cs:379`, `Receipt/ReceiptVerifier.cs:553`; php
`Jws/JwsVerifier.php:256-258`, `Receipt/ReceiptVerifier.php:257`; python
`jws.py:309-311`, `receipt.py:256`; ruby `jws.rb:271`; node `jws.ts:126`;
swift and go decode every certificate when parsing it). The 0.7 rewrite
decodes a key only once its certificate is vouched for, matching Java.

**Test that proves it.** On both paths, an oversized key in an untrusted
certificate fails as UNTRUSTED_CHAIN without any verification using that key,
within the shared time budget. The port asserts "without any verification"
directly (a counting seam around its issuer check, or equivalent), not only
by timing.

### Change 3: any receipt signer algorithm

| Port | Status | Evidence |
|---|---|---|
| go | MISSING | RSA only and SHA-1/SHA-256 only, `receipt.go:344`, `:349-359` |
| swift | MISSING | `ReceiptVerifier.swift:500-501`, `:575` |

| node | MISSING | `src/cms.ts:25-28`, `src/receipt.ts:328` |
| rust | in progress in the 0.7 work | |

.NET and PHP must also iterate SignerInfos themselves, per the 0.7 design.
Whether an MD5 digest is accepted waits on Q15.

**Test that proves it.** Receipts signed under the test PKI with an ECDSA
P-256 signer and with a SHA-384 digest each verify; the same receipts with
one content byte changed are INVALID_SIGNATURE.

**RSA-PSS is port-defined** (owner, 2026-09-27). Apple never signs receipts
with RSA-PSS, so it is not part of the guaranteed set. A port may verify a
PSS signer or refuse it as INVALID_SIGNATURE; the shared case
`receipt/signer-rsa-pss-does-not-crash` only pins that the call returns
without a crash or INTERNAL_ERROR. PHP refuses it: `openssl_verify()` has no
PSS mode, and verifying PSS there would mean hand-written EMSA-PSS on the
forgery path, where the signer picks the algorithm. The tampered PSS receipt
stays INVALID_SIGNATURE in every port.

## Shared cases to add to fixtures/cases-0.7.json

1. An oversized key in an untrusted `x5c[1]` fails as UNTRUSTED_CHAIN without
   any verification using that key, within the shared time budget.
2. A receipt whose only intermediates are untrusted certificates with
   oversized keys fails as UNTRUSTED_CHAIN without any verification using those
   keys, within the shared time budget.
3. A genuine receipt padded with stranger certificates, including one with an
   oversized key, verifies (Q16).
4. Receipt signers with an ECDSA key and a SHA-384 digest each verify under
   the test PKI, and an RSA-PSS signer does not crash (port-defined, see
   change 3); one content byte changed is INVALID_SIGNATURE.
5. A genuine receipt without signed attributes, with one content byte
   changed, is INVALID_SIGNATURE.
6. A four-segment JWS is MALFORMED.
7. Apple's pre-2018 purchase-info receipt is MALFORMED (21002 at the
   endpoint).
8. A JWS whose `alg` carries control and line-separator characters is
   MALFORMED, and the case notes that the message must not contain them (ports
   assert this in their own runner).

The time budget is one figure shared by all ports, set in the case file.

## Measurements behind change 1 (audit, 2026-09-27)

The owner chose to publish the measured detail (Q18, Q19). All figures come
from the audit container and are single runs, not benchmarks.

- **Every non-Java port** walks the chain from the leaf upwards, so a
  certificate's signature is checked with the next certificate's key before
  any pinned root has vouched for that key.
- **Go:** `crypto/rsa` has no cap on the modulus size, only on the public
  exponent (2^31 - 1). One RSA verify took 21 ms with a 16,384-bit key,
  317 ms with 65,536 bits and 5.2 s with 262,144 bits. Through the public API,
  one forged JWS of 118,425 bytes cost 5.34 s of CPU and returned
  `INVALID_CHAIN`. The receipt path is extrapolated to minutes per request
  (not measured). Besides the top-down walk, Go also gets a modulus cap of
  8,192 bits checked before any verify.
- **Ports on OpenSSL** (Node, Ruby, PHP, Python, .NET on Linux): OpenSSL
  caps the modulus at 16,384 bits and, above 3,072 bits, the exponent at
  64 bits. The worst single verify measured was about 6.5 ms; a receipt can
  force about 54 verifies, so about 0.35 s per request (estimate).
- **Swift:** BoringSSL refuses RSA keys above 8,192 bits or with an exponent
  above 33 bits when it parses them, so the cost is bounded (about 1 ms per
  verify, estimate).

Not measured: Python, .NET on Windows and macOS, PHP, Swift, the Node web
build under non-Node WebCrypto, pre-trust decoding of EC keys with explicit
curve parameters, and the Go receipt path.
